# 信件分拣优先级引擎

`server/priority.js` 为调度台提供**确定性的信件分拣优先级队列**：综合加急等级、
截止窗与目的地约束计算软优先级分，支持可撤销的人工覆盖，且覆盖在任何情况下
都不能绕过硬规则。

## 设计目标

| 目标 | 实现 |
| --- | --- |
| 综合加急、截止窗、目的地 | 三要素各自独立计分后相加，分解值随队列返回，可解释 |
| 同一输入结果稳定 | 纯函数计算、整数定点分、全序排序键、输入预排序 |
| 人工覆盖可撤销 | 事件溯源日志（apply/revoke），撤销即失效，全程留痕 |
| 覆盖不得绕过硬规则 | 写入时校验 + 读取时二次裁决；覆盖只能调整软分且限幅 |

## 评分模型（软规则，整数分）

```
总分(0..6000) = 加急分(0..3000) + 截止窗分(0..2000) + 目的地分(0..1000)
```

- **加急分**：常规/优先/加急 = 1000/2000/3000，级距 1000 分。
- **截止窗分**：先求物理余量 `slack = (截止日 - 今日) * 24 + 截止时 - 最早可达时刻`。
  余量 ≤ 0（含积压件）记满分 2000，余量 ≥ 15 小时记 0 分，其间线性递减。
  "最早可达时刻"用单件直航估计（当日风况 + 最快可承运信使），是送达时间的物理下界。
- **目的地分**：运输时长分（直航耗时 × 2，上限 600）+ 承运稀缺度分
  （可承运信使越少分越高，上限 400），合计封顶 1000。

## 硬规则（覆盖不可绕过）

1. **状态**：只有 `inbox` / `backlog` 邮件进入分拣队列；已投递邮件不可覆盖。
2. **承运能力**：邮件重量超过所有信使载重 → 进入异常队列
   （`NO_FEASIBLE_COURIER`），拒绝施加覆盖。
3. **物理可达性**：`deadlineFeasible` 由直航下界推导，覆盖只改分数，改不了这个标志。
4. **容量约束**：建议装载（`suggestion`）按优先级贪心装填，严格遵守各信使的
   载重与件数上限；装不下的邮件进入 `skipped`（`CAPACITY_EXHAUSTED`），
   覆盖只能改变谁优先装，不能让任何信使超载。

## 确定性保证

- `computePriorityQueue(state)` 不读系统时钟、不用随机数，输出完全由 `state` 决定。
- 评分使用整数分（余量先量化到 1/100 小时再取整），无浮点累计误差。
- 排序键为全序：`分数 → 截止日 → 截止时 → 加急级 → 邮件 id`，id 唯一，杜绝并列。
- 计算前按邮件 id 预排序，输入数组顺序不影响输出。
- 字符串比较使用字典序而非 `localeCompare`（后者随运行环境语言而变）。

## 人工覆盖语义

- 覆盖事件存放在 `state.priorityOverrides`（append-only），随存档持久化。
- `apply`：参数 `delta` 必须是 ±900 内的非零整数（小于一个加急级距 1000，
  因此覆盖不能独自跨越完整加急等级），且必须填写 `reason` 以便审计。
  同一封邮件只保留一条有效覆盖，新覆盖会自动撤销旧覆盖（留痕）。
- `revoke`：追加一条 revoke 事件指向目标 apply，立即生效；重复撤销会被拒绝。
- **当日有效**：事件携带 `day`，跨日结算后自动失效（日志保留，可审计）。
- 双重防线：写入时校验邮件状态与承运能力；读取时异常队列的裁决先于覆盖应用，
  即使日志里存在针对异常邮件的覆盖事件也会被忽略。

## API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/game/priority` | 当前分拣队列（含分数分解、异常、覆盖日志、建议装载） |
| POST | `/api/game/priority/overrides` | 施加覆盖 `{ letterId, delta, reason }` |
| DELETE | `/api/game/priority/overrides/:id` | 撤销指定覆盖 |
